详细摘要，
什么时候真有用。

我们给框架加了一个"详细摘要"开关——把长对话压成九段结构、逐字保留用户消息。 它到底有没有用？跑了三轮真实 benchmark，结论是：它不是万能银弹，而是"让纯摘要就够强"的手段， 跟"按需检索"是替代关系，不是叠加。下面用数据说话。

第一部分 · 这轮改了什么

一个开关，把摘要从“一句话”变“九段”

框架本来就会在对话变长时生成摘要、塞进后续上下文。默认的摘要 prompt 很简短。我们加了一个 WithDetailedContinuityPrompt() 开关，开后摘要变成九段固定结构——重点是把所有用户消息逐字保留，并指向按需恢复工具。设计参照了 Claude Code 的压缩 prompt，但接的是本框架自己的 session_search / session_load。

默认摘要实测产出 ~2 千字符

分析对话，给一份聚焦“对未来有用的重要信息”的简洁摘要——点到为止、只留相关的、别杜撰。

Analyze the following conversation ... and provide a concise summary focusing on important information that would be helpful for future interactions. Keep the summary concise and to the point. Only include relevant information. Do not make anything up.

追求简洁无结构不逐字保留
详细摘要（本轮新加）实测产出 ~5 万字符

把对话压成九段固定结构，重点逐字保留所有用户消息，并告诉模型缺细节时用检索工具捞回、别重调工具。（详情见下方九宫格）

Your task is to produce a detailed, structured summary ... Structure your summary with these sections: 1. Primary Request ... 6. All User Messages (verbatim) ... 9. On-Demand Recovery ...

九段结构逐字用户消息指向按需恢复
§1
主要请求与意图
记下每一条用户请求，包括意图变化。
§2
技术概念与决策
关键概念、技术选型、被否决的方案及原因。
§3
文件、代码与工具调用
改过哪些文件、调过哪些工具、关键结果。
§4
错误与修复
踩过的坑怎么填的，尤其用户纠正的话逐字记。
§5
关键事实与约束
日期、数字、配置值、ID——标准化留存。
§6
全部用户消息（逐字）
所有非工具结果的用户消息，逐字保留，不改写。
§7
待办任务
明确要求过但还没做完的事。
§8
当前工作
摘要前一刻在做什么，带最近消息原文，便于接续。
§9
按需恢复
被压掉的内容别重调工具，按 event_id 用检索工具捞回。
两个关键段落决定了它的特性：§6 逐字保留用户消息，让摘要信息密集、可被关键词搜到；§9 明确告诉模型"缺细节去检索，别重调工具"。这两点正是后面"详细摘要 vs 按需检索"故事的伏笔。
第二部分 · 三场考试

短对话、长对话记忆、知识更新

同一个"开/关详细摘要"，扔进三个场景考。每个场景的对话长度、考查目标都不一样，结论也不同——这正是"什么时候有用"的答案所在。

考试一 · 短对话

MT-Bench-101 多轮对话

每条 4 轮 · minimax-m3 · 3 case
不省 token 详细摘要反而多花 5.3% prompt（摘要本身更长，节省来不及累积），但信息保留率从 0.52 升到 0.69。短对话不是它的主场。
考试二 · 长对话记忆

LongMemEval multi-session

~105K token · glm-5.2 · 4 case
纯摘要碾压 详细摘要的纯摘要质量是默认的 7.46 倍，命中率达到 75–100%（默认仅 25–50%）。详细摘要让纯摘要就够强。
考试三 · 知识更新

LongMemEval knowledge-update

用户更新事实 · glm-5.2 · 4 case
检索帮倒忙 详细摘要逐字保留了更新后的事实，纯摘要答得准；但配上按需检索反而召回旧版本，质量从 0.23 掉到 0.12。强摘要 + 检索 = 浪费。
第三部分 · 考试一展开

短对话里，它没省 token，但更准

多轮对话只有 4 轮，而摘要要等到第 3、4 轮才触发——节省根本来不及累积，详细摘要本身又更长，prompt 反而更费。但信息保留明显更好。这条线索指向：它的价值在"信息保留"，不在"省 token"。

第五部分 · 核心发现

按需检索是“兜底拉平器”，不是放大器

这是最反直觉的一条。原本以为"详细摘要 + 按需检索"会强上加强。实测却相反：检索把弱的默认摘要拉到和详细摘要差不多，但对已经很强的详细摘要帮不上忙、甚至帮倒忙。上一轮"检索让详细领先 3 倍"的说法，这次没复现——真相更本质。

为什么详细摘要 + 检索反而变差

知识更新类问题问的是"用户更新后的最新值"。详细摘要的 §6 已经逐字保留了更新后的事实，模型直接答就准。这时再触发按需检索，反而可能召回旧版本的事实，把模型带偏——质量从 0.23 掉到 0.12。检索是给"抓不住事实的弱摘要"兜底的，不是给"已经抓得住的强摘要"锦上添花的。

第六部分 · 一张图说清

摘要越强，检索从"帮忙"变"帮倒忙"

把三个场景的发现抽象成一条规律：横轴是摘要信息密度（从默认的弱摘要到详细的强摘要），纵轴是相对回答质量。两条线——纯摘要、摘要+检索——在中间交叉：左边检索把弱摘要拉起来，右边检索反而把强摘要拉下去。交叉点就是检索的"盈亏分界"。

摘要强度 × 检索 · 回答质量走向
概念示意 · 合成 multi-session 收敛 + knowledge-update 反转两趋势

一句话：摘要和检索是替代关系，不是叠加。两条线在中间交叉——左边检索帮忙，右边检索帮倒忙。

  • 左弱摘要区（默认）：纯摘要抓不住事实，加检索能把质量大幅拉起来——检索是兜底，增益为正。
  • 右强摘要区（详细）：摘要已逐字保留事实，检索增益趋零；知识更新场景还会反转——检索召回旧事实，质量反被拉低。
  • ∴别同时上：要么详细摘要自己扛（省检索延迟/token），要么默认摘要 + 检索兜底，两条路终点接近。

图为概念示意，合成“multi-session 收敛”与“knowledge-update 反转”两条趋势，非单次实验精确曲线；定量数据见上方柱状图。纵轴“相对质量”仅作高低示意，无绝对分值。

第七部分 · 落到决策

什么时候开详细、什么时候配检索

把发现收口成一张选择表。纵轴是"配不配按需检索"，横轴是"用哪种摘要"。两个推荐格子终点质量接近，但路线不同——一个靠摘要自己扛，一个靠检索兜底。

默认摘要（弱）
详细摘要（强）
不配检索
✗ 不推荐
信息丢失
弱摘要抓不住关键事实，又没检索兜底，长对话里基本答不对。
★ 推荐
摘要自己扛
详细摘要信息密集、逐字保留事实，模型直接答就准。省掉了检索的延迟和 token 开销。适合长对话记忆、知识更新。
配检索
✓ 可行
检索兜底
弱摘要 + 按需检索能把质量拉回来。适合不想付详细摘要成本、又能接受工具调用延迟的场景。
✗ 浪费
检索帮倒忙
强摘要已经把事实留在摘要里，再检索召回冗余或过时信息，反而干扰。知识更新场景实测质量掉一半。
一句话

要详细摘要就别再叠检索（让它自己扛）；要省摘要成本就默认摘要 + 检索兜底。两条路终点接近，别同时上。

第八部分 · 意外收获

跑 benchmark 顺带挖到三个问题

真实环境跑长上下文 benchmark，逼出了一些读代码发现不了的问题。前两个是框架 bug，已记进待办；第三个是模型选型教训。

T10
pgvector 写死了不合法的时区名

框架的 session/pgvector 有 16 处 SQL 写死了 NOW() AT TIME ZONE 'localtime'。localtime 不是合法的时区名，在这台机器上直接报 SQLSTATE 22023。当时靠建一个 zoneinfo 软链绕过，根因是 SQL 不该硬编码这个字符串。

T11
embedding 维度默认 1536，不按模型自适应

换 ollama 的 nomic-embed-text（768 维）时，embedder 默认还是 1536 维，向量表建错维度、embedding 写入全失败。根因是 embedder 层应按实际模型维度自适应或要求显式传参，而不是写死 OpenAI 的 1536。

选型
minimax-m3 不会主动调工具

在按需检索模式下，minimax-m3 四个 case 全是 tools=(0/0)，完全不调 session_search。同配置 glm-5.2 能正常调（每 case 1–8 次）。这是模型指令遵从问题，不是框架 bug。需要工具调用的场景别用 minimax-m3，用 glm-5.2 这种遵从度好的。

局限说明

8 个 case 仍是小样本，逐 case 波动大（比如知识更新里有个 case，详细纯摘要 0.64 但加检索掉到 0.31）。只测了 glm-5.2 一个模型，ROUGE-L 对长回答不友好会放大噪声。结论是趋势性的，要定量精确还得扩到 20+ case。完整日志在 /tmp/lme-glm-*.log。不过这一轮 benchmark 就花了将近 4 个小时，更详细的评测留到未来收集一轮新优化了再跑。
