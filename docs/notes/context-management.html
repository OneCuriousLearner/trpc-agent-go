第一部分 · 上下文长什么样

第二部分 · 组装链路

谁往上下文里塞东西

一次 LLM 调用前，框架跑一串"请求处理器"（RequestProcessor），按固定顺序往同一个 Request 里加内容。每个处理器只管自己那一份，合在一起就是最终上下文。

1
BasicRequestProcessor填生成参数：stream / temperature / max_tokens / thinking，以及 provider 特有的顶层字段和 HTTP 头。
2
InstructionRequestProcessor · system 主体合并出 system message：SystemPrompt 放前面、Instruction 放后面；支持 {{state.xxx}} 占位符渲染；有结构化输出 schema 时追加 JSON 输出指令。
3
ContentRequestProcessor · 历史拼接（核心）从 session 事件拼历史消息：摘要 / 预加载记忆 / 召回注入；reasoning_content 处理；context compaction 的 Pass 0/1/2 在这跑；最后加当前用户消息。
4
SkillsRequestProcessor · 技能注入技能概览 Available skills: + 已加载技能正文 [Loaded] <name> + 文档，合并进 system（开了 WithSkillsLoadedContentInToolResults 则进 tool result）。
5
PostToolRequestProcessor · 工具指引有工具就注入 [Tool Prompt]：分析工具结果、别重复调同样工具、最终答案要简洁等指引。
6
工具装载invocation.Agent.Tools() → req.Tools，含函数工具、MCP、skill、transfer_to_agent、knowledge_search、session_search 等。
7
身份 / 规划 / 条件 / 时间戳等按需注入：当前时间、身份信息、规划状态、条件分支等。
关键设计

system message 始终被合并成一个——instruction / 摘要 / 记忆 / skill / 工具指引都往同一个 system 里塞，而不是产生多个。这是为了兼容 Qwen 等不支持多个 system message 的模型。"rules"（类似 CLAUDE.md）就是 Instruction 的一部分，没有专门的读取机制，调用方自己塞进 WithInstruction(...)。

第三部分 · 接近极限

三层流水线，依次兜底

上下文逼近极限时，三层按顺序裁：
第一层在组装阶段把大工具结果压成可恢复占位符，
第二层在超阈值时同步刷摘要重建，
第三层在发请求前硬删中间整轮。
前两层可恢复，最后一层是保命硬删。

第一层

context_compact · flow 层

组装阶段 · preprocess

对"已筛过的工具结果"跑三个 Pass，按固定顺序，改的是 tool result 的 Content：

  • Pass 0 · ForceCleanToolNames 命中的工具结果 → 强制替换成策略占位符不可恢复
  • Pass 1 · 历史 tool result 超 ToolResultMaxTokens（默认 1024）→ 替换成带 event_id 的占位符可恢复
  • Pass 2 · 任意 tool result 超 OversizedToolResultMaxTokens（默认关）→ 首尾保留、中间截断部分可恢复

受保护：当前请求 + 最近 KeepRecentRequests 个完成的请求 + SkipRecentFunc 指定的尾部。Enabled=false 是"框架不动工具结果"的总开关。

第二层

maybeCompactContextBeforeLLM · 同步摘要

preprocess 之后、callLLM 之前

当 token 超过 context window × 0.7（下限 2000）时触发，是唯一产生 API 成本的层：

  • 同步调 CreateSessionSummary 生成 / 刷新摘要
  • 摘要有推进 → clone 组装前的快照、重跑 ContentRequestProcessor（注入新摘要 + Pass 0/1/2 再跑一遍）+ 重放 skill 正文
  • 有熔断器：连续失败 3 次就停（per-run 计数。原本没有，我们参考 Claude Code 线上故障新增的）
第三层

token_tailor · MiddleOut · model 层

发请求前最后兜底

provider 内按 token budget 删中间整轮消息（Lost-in-the-Middle 理论）：

  • 保 system 头 + 最后一轮，删中间 user-anchored 轮次
  • 最小保护上下文（system + 末轮）仍超 → 返回 overflow error，不静默丢 system不可恢复
职责边界

可恢复归 flow 层（占位符带 event_id + session_load 闭环），硬预算保命归 model 层（tailoring 硬删中间整轮）。两层正交——flow 层改的是 tool result 内容，model 层删的是消息轮次，互不干扰。

第四部分 · 压缩实测

2675 字节，怎么变成 447

同一个工具结果，第一轮完整保留（当前请求受保护），第二轮被 Pass 1 压成占位符。
占位符里带着 event_id 等恢复线索——压缩不是有损丢弃，是把原始数据移出活动上下文、按需能捞回来。

压缩前 · 第一轮
2675bytes
role=tool · 当前请求受 KeepRecentRequests 保护
{"summary":"generated 20 synthetic log lines","log":"line 0000 service=payment shard=00 level=INFO request_id=req-0000 message=\"synthetic diagnostic payload...\" line 0001 service=payment shard=01 ... ... ... ... ...(共 20 行，每行约 130 字节)... ... ... ... line 0019 service=payment shard=03 level=INFO request_id=req-0019 ..."}
PASS 1 压缩
省 83%2228 bytes
压缩后 · 第二轮
447bytes
role=tool · 变成历史，被 Pass 1 替换为占位符
[elided] Previous tool call succeeded and its result was already consumed by the assistant; payload has been dropped to save context. Do NOT re-invoke the same tool... event_id: da4762c2-c10c-4b8... tool_call_id: call_306699f5... tool_name: large_log reason: historical_compaction Use session_load with event_id and content_offset/content_limit if the full result is needed.
可恢复闭环

模型发现还需要那段被压掉的内容时，按占位符里的 event_id 调 session_load 工具，就能从 session 里精确取回原始完整结果（还支持 content_offset / content_limit 切片）。实测中模型靠前面 assistant 写下的总结就答对了，没触发取回——但取回通道是通的。

第五部分 · 怎么导出给前端

把上下文结构变成 JSON

未来要给前端展示"消息顺序、token 估算、原文对照"，先得找到能拿到最终请求的接入点。
下面是现状评估——只有一个点能拿到完整且可改写的真源。

能力位置够不够「顺序+token+原文」
BeforeModel 回调 model/callbacks.go:64，调用于 llmflow.go:2316 ✓ 完整真源
Messages 顺序、Tools、生成参数都在；token 用 TokenCounter 算；可改写
OTel trace span llmflow.go:1102 → telemetry/trace.go:558 △ 受截断
完整请求 JSON + gen_ai.input.messages；受 SpanAttributePolicy 截断，只能事后看
preprocessing 事件流 processor/*.go ✗ 不含原文
只是各处理器"我处理了什么"的状态信号
AG-UI SSE server/agui/ ✗ 不暴露
只翻译 Runner 事件流（user/text delta/tool call）给前端，不含 request messages
latency diagnostics llmflow/diagnostics.go ✗ 只给计数
只记 messages/tools 数量和耗时，适合性能诊断

推荐方案：BeforeModel 回调 + 自定义事件

真源就是 BeforeModel 看到的那个 *model.Request —— 没有比它更真的了
  1. 写一个 BeforeModel 回调，把 args.Request.Messages 映射成 [{index, role, tool_name, tool_id, content, content_parts, tool_calls, estimated_tokens}]，附总量、tools 列表、生成参数。token 用 TokenCounter 接口（内置 SimpleTokenCounter，也可换 tiktoken 精确预估）。
  2. 回传通道：Runner 事件流目前没有"上下文快照"事件类型。最轻量做法是用 event.WithExtension(key, payload) 挂一个自定义事件，agui 已能透传自定义事件，前端按 extension key 取。
  3. 次选：若前端已接 OTel collector，直接读 gen_ai.input.messages.otel span attribute，零代码改动——但受截断策略影响，只能事后看。
