五个模块，
怎么 搭到一起。

trpc-agent-go 把工具、MCP、技能、会话、记忆五样东西， 在一次调用里拼成一个整体交给 Agent 用。Agent 干活时， 工具又反过来找会话和记忆拿数据。这条来回的通路，就是理解整个框架的钥匙。

图 1 · 一次调用怎么走 
用户发一条消息进来
  │
  ├─ 先把这次对话的草稿本翻出来     ──► 会话服务     // 有就加载，没有就新建
  ├─ 把几样东西打包成一个执行上下文
  │   里面塞好：会话、记忆、工具、技能
  │
  ├─ 让 Agent 开始干活  ◄──  工具要数据时，从这个上下文里找
  │   └─ 比如记忆工具会从上下文里拿到记忆服务，搜索工具会拿到会话服务
  │
  └─ Agent 干完，做收尾            ──► 触发记忆提取 · 把对话丢给外部记忆平台
第一部分 · 五个模块

五样东西分别是什么

先别管接口名，用大白话讲清楚每个模块是干嘛的。源码里的英文名字放在括号里，方便你去代码里对照。

模块一工具系统

工具箱Tools

Agent 干活用的扳手、螺丝刀。框架定了一套标准接口，让任何工具都能挂进来给模型调用。

打个比方 一个工具最起码得有张说明书——叫什么名字、干什么用、要什么参数。能被调用的工具，就多一个「执行」能力。能边跑边吐结果的工具，就再加个「流式」能力。一把把工具打包成一盒，就是工具箱。
这套系统还管这几件事
  • 谁能被看到：决定哪些工具对模型可见（filter 过滤）
  • 能不能执行：工具真要跑前过一道权限（permission），不让跑就拦下
  • 失败重试：工具临时报错时自动重试（retry）
  • 执行前后插手：跑之前能改参数，跑之后能改结果（callbacks 回调钩子）
  • 多个结果合并：并行调多个工具时把结果拼起来（merge）

最常用的工具是函数工具（function），你写个 Go 函数，框架用反射自动生成参数说明，不用手写。

模块二外接工具协议

外接工具的两种进货方式MCP

MCP 是个开放协议，让 Agent 能调用外部服务提供的工具。框架给了两套接法，对应两种进货思路。

打个比方 方式一像把整箱工具搬回家摆好，要用直接拿——快、顺手，但占地方。 方式二像家里只放个目录，要哪个再打电话去仓库问、去取——省地方，但多跑一趟。

方式一 · 整箱搬回家

直接挂载，启动时连好
适合什么场景
工具少、固定、常用的服务
怎么干
启动就连好远端服务，把它的每个工具直接当成 Agent 的工具摆好
好处
调用最快，能带上远端的安全标记（比如「只读」「有破坏性」）做权限判断
代价
工具多的时候，光工具说明就占不少上下文

方式二 · 要哪个去取

按需发现，用到了才查
适合什么场景
工具很多、大部分用不上、或者经常变的服务
怎么干
只给模型四个「中转工具」：先列有哪些服务、再看某服务有什么工具、再查某工具的参数、最后才调用
好处
省上下文，适合长尾和动态能力
代价
每次都要现查，整体慢一些，也不会带远端的安全标记

两种方式可以一起用：常用的核心工具走方式一直接挂，长尾的走方式二按需取。

模块三技能仓库

说明书库Skill

把复杂任务封装成一本本「说明书」（一个目录带一份 SKILL.md），需要时翻开，不需要时不占地方。

打个比方 就像家里有一摞说明书——做菜、修电器、报税。平时收在柜子里不占台面， 需要哪本就翻哪本。模型先看到的是每本说明书的一行简介，真正要用时才把正文打开。
三层信息，逐层打开
  • 第一层 · 看到名字：只把每本说明书的名字和一句话描述塞进提示词，让模型知道「有这些技能可用」
  • 第二层 · 翻开正文：模型觉得要用某技能，调一个工具把 SKILL.md 正文加载进上下文
  • 第三层 · 跑脚本：技能里带的脚本不会塞进提示词，而是在隔离的工作区里执行，只把结果带回来
  • 技能的加载状态记在会话里，按哪个 Agent 加载的分开存，所以多个 Agent 共用一次对话时不会互相串
  • 说明书可以从本地目录读，也可以从网上的压缩包下载解压
  • 跑脚本需要「代码执行器」配合——把技能目录搬进工作区再执行
模块四会话管理

这次对话的草稿本Session

记着这一次对话说了什么、中间结果是什么。按「哪个应用、哪个用户、哪次对话」分开存，对话结束就翻篇。

打个比方 像开会时手边的草稿本——记着这次讨论的来龙去脉。开新会就换新本子。 本子里还夹着几张便利贴（状态），比如「技能 A 已经加载了」「上次摘要到哪了」。
这个模块管这几件事
  • 存取对话：加载已有对话、追加新消息（GetSession / AppendEvent）
  • 自动摘要：对话太长时，后台用模型压成一段摘要，省 token（EnqueueSummaryJob）
  • 状态读写：存各种小标记，应用级、用户级、本次对话级各管各的
  • 钩子：消息写入前后能插一手，比如自动给消息分类打标签
  • 支持内存、SQLite、Redis、Postgres、MySQL、ClickHouse 等多种后端，共享逻辑抽在 internal/，各后端只写存储部分
  • 两个可选能力：按语义搜历史消息和按锚点精确取某段消息——需要后端支持，所以这两个工具是按后端能力动态挂的
  • 还有个「投递口」机制（Ingestor），专门把整段对话丢给外部记忆平台
模块五长期记忆

这个人的人物档案Memory

按「哪个应用、哪个用户」存的人物档案，跨对话不丢。记的是「他叫张三、喜欢 Go、在腾讯」这种稳定事实。

打个比方 会话是短期记忆（这次聊了啥），记忆是长期记忆（这个人是谁）。 换对话不会丢——下次他再来，你还记得他喜欢什么。

方式一 · 工具驱动

Agent 自己决定记什么

把「存记忆」「搜记忆」这些工具交给 Agent，它在对话里判断要不要记，用户能看到它调用工具的过程。适合需要精确控制记什么的场景。

方式二 · 自动提取（推荐）

后台默默学，用户无感

配个提取器，每轮对话后后台跑模型分析「这轮有什么值得记的」，自动存下来。用户只看到对话，感知不到后台在学。

  • 同一条内容重复存不会变多条——按内容算指纹，相同就覆盖更新
  • 支持内存、Redis、MySQL、Postgres、pgvector 等后端，检索算法共享在 internal/
  • 外部记忆平台（mem0、腾讯的 TencentDB）走投递口接入：只把对话丢过去，存取都由外部平台管
第二部分 · 调用时序

模型说要调用工具后，发生了什么

从模型说要调用工具，到把结果送回模型，中间要过一道道关。改工具相关代码时最易踩错的就是这个顺序，尤其权限检查用的是「改完之后」的参数，不是模型最初给的那版。

01
模型说要调用工具框架拿到模型要调的工具列表。
02
先把参数修一修（可选）模型给的参数有时不是合法的 JSON，尽力补好，避免后面执行失败。
03
给这次调用贴个编号存进上下文，工具实现能拿到这个编号打日志、做埋点。
04
跑执行前的钩子可以改参数、甚至直接返回结果不真跑了（callbacks 回调）。
05
敲定最终参数权限检查看的是这版参数——经过修复和钩子改写后的，不是模型最初那版。
06
查权限工具自己的检查先跑，运行时的策略后跑；不让跑就拦下，返回「被拒绝」或「需要审批」。
07
真正执行普通工具失败可按策略重试；流式工具边跑边吐数据。
08
跑执行后的钩子可以替换结果，或要求「跳过总结」直接结束这轮。
09
把结果转成回模型的消息转成模型能看懂的格式。
10
送回模型继续想模型拿到工具结果，继续推理。
第三部分 · 接线图

六个模块怎么互相找

这是全页的核心。模块不是各干各的——搜索工具按后端能力自动决定挂不挂、记忆工具从上下文反找服务、跑脚本要靠代码执行器、MCP 中转站和技能互为信息源、压缩掉的内容能按线索捞回来、外部记忆平台走投递口而不是直接接管。每条线都说清了谁需要谁、为什么。

会话的两个搜索工具session_search · session_load
按后端能力自动挂
会话服务要看后端支不支持向量检索
线 一这两个工具不是写死的——每次调用时，框架会看后端支不支持语义搜索和按锚点取消息，支持才挂对应的工具。换个不支持的后端，搜索工具自动消失。
记忆工具存、删、搜记忆
从上下文反找服务
记忆服务上下文里挂的那份
线 二工具自己不绑死某个后端，运行时从执行上下文里把记忆服务拿出来用，再从会话里取用户身份。所以换后端不用改工具。
跑脚本工具skill_run · skill_exec
搬进工作区再执行
代码执行器提供运行环境
线 三跑脚本的工具先把技能目录搬进一个隔离的工作区，再让代码执行器在里面跑命令。这俩是独立的开关——配了执行器只是让跑脚本能用，不会顺手把别的代码也跑了。
MCP 中转站需要时去连外部
技能告诉去哪连
技能仓库提供地址和能力说明
线 四中转站只管「怎么连、怎么调」，但它不知道「为什么要连这个」。技能正好补这层——技能加载后告诉模型「有这么个外部服务、地址是这个、能干这些」，模型再让中转站去连。
上下文压缩对话太长时压一压
留线索，按需捞回
按需取回工具session_load
线 五压掉的内容不是真删，而是留个线索（事件编号）。模型发现还需要那段内容时，用取回工具按线索捞回来。压缩是移出活动区，不是有损丢弃。
外部记忆平台mem0 · TencentDB
走投递口，不接管
会话投递口Ingestor · 框架只丢不管
线 六这些外部平台不归框架直接管——框架只在每轮结束后把整段对话丢过去，存取都由平台自己来。「框架直管记忆」和「丢给外部」是两条不同的路。
第四部分 · 一次调用

一次调用从头到尾怎么走

会话服务在整个过程里被反复用；记忆服务只在收尾用一次；投递口也只在收尾用一次。还有个重点：摘要是在每条消息写完后顺手触发的，不是等全部跑完才做。

1
准备会话有就加载，没有就新建一个。
2
登记这次调用绑一个「取消按钮」，方便随时叫停。
3
接好事件追加器Agent 每吐一个事件，自动落进会话里。
4
开跑 Agent驱动 Agent 干活，消费它产出的事件流。
5
边跑边记每条事件存进会话，顺便看看要不要做摘要。
6
收尾触发记忆提取、把对话丢给外部记忆平台。

怎么随时叫停一次调用

调用方先给这次调用起个名字（请求 ID），框架把这个名字和一个「取消开关」绑在一起存进表里。想叫停时，拿这个名字一查、一按，这次调用就停了。

// 调用方给这次调用起个名字 WithRequestID(id) ─► 这次调用的名字 // 框架把名字和取消开关绑一起 registerRun(id, 取消开关) ─► 存进表 // 想叫停时 Cancel(id) ─► 查表 ─► 按取消开关 // 跑完或叫停后 注销(id) ─► 从表里删掉，防泄漏

要叫停一次调用，应该去按这个取消开关，而不是在读取结果时直接跳出循环——因为 Agent 可能还在后台往通道里写，你跳出了它写不出去，就会卡住、漏内存。

第五部分 · 有意为之

几个故意这么设计的地方

改这些模块时，下面这些是「故意这么设计的」，别无意中改坏了。

搜索工具是动态挂的，不是写死的

每次调用时，框架会看会话后端支不支持向量检索，支持才挂搜索工具。换个不支持的后端，搜索工具自动消失。改这块要保留这个「按能力动态挂」的机制。

共享逻辑别在每个后端重复写

会话和记忆都把共享逻辑（摘要编排、检索算法、分页排序）抽在 internal/ 里，各后端只写存储。改检索或摘要逻辑优先改 internal/，别去每个后端改一遍。

叫停要走取消开关，读到通道关闭

按取消开关后，Agent 会停下来、事件流会关闭，读取结果的一方要把通道读到关闭为止。这是事件流框架的通用约定。

「框架直管」和「丢给外部」是两条路

记忆服务（MemoryService）是框架直接管记忆的 CRUD 和自动提取；投递口（Ingestor）是框架只把对话丢给外部平台、不管存取。新增外部记忆平台，优先走投递口这条路。

技能的加载状态按 Agent 分开存

「技能 A 已经加载了」这种状态，是按哪个 Agent 加载的分开存的，所以多个 Agent 共用一次对话时不会互相串。改技能相关逻辑要保留这套隔离。

权限检查看的是改完之后的参数

权限检查用的参数，是经过「JSON 修复 + 执行前钩子改写」之后的最终版，不是模型最初给的那版。改权限逻辑要基于这个前提。

后台任务的错误不容易看见

记忆自动提取、复盘这类活儿在后台跑，报错了只落一条警告日志。要想「后台连续失败」能被发现，得加计数器或回调上报，光看日志发现不了。
